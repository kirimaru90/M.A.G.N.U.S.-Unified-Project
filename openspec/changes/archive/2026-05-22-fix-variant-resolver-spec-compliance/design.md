## Context

A spec-compliance audit found six divergences between the reference docs, specs, and engine:

1. `node-resolver.js` reads `variant.condition`; both reference docs and all examples use `variant.when`.
2. Both reference docs describe a `{ "key": "...", "eq": value }` inline-operator condition grammar. The evaluator (`conditions.js`) has always parsed `{ "var": "...", "op": "...", "value": ... }`. The two shapes are incompatible — content written to the docs would silently fail.
3. The `not` combinator is implemented and spec'd but missing from both reference docs.
4. `resolveNode` always returns `node.components`; per-variant `components` are silently ignored.
5. `showChoices()` renders every choice unconditionally; the authoring guide §5.3 specifies that a choice with a `when` field is hidden when the condition is false.
6. Neither reference doc carries version or date tracking.

Since content is generated by AI agents or GUI editors (not typed by hand), the `var/op/value` grammar is strictly better: it is regular, JSON-Schema-validatable, and maps cleanly to `switch (condition.op)`. The reference docs are updated to match the implementation — not the other way around.

## Goals / Non-Goals

**Goals:**
- Engine reads `variant.when` for variant selection.
- Engine resolves `components` as: matched variant's `components` if defined, else `node.components`.
- `showChoices()` evaluates each choice's `when` condition against the current snapshot and hides choices that evaluate to false.
- Both reference docs (`terminal-authoring-guide.md`, `robco-terminal-architecture.md`) updated to use the `var/op/value` condition grammar (dropping the `key`/inline-operator format that was never actually supported by the evaluator).
- Both reference docs gain a YAML version header (`version`, `date`) at the top.
- `not` combinator added to both reference docs (it is already implemented and in the spec; the docs just never documented it).
- `conditional-variants` spec updated (field name + per-variant `components` override semantics).
- `input-components` spec corrected: branch condition field renamed from `condition` to `when`.

**Non-Goals:**
- No new authoring features beyond what is already implemented.
- No changes to `index.html`, CSS, or API contracts.
- No changes to `conditions.js` — it already uses the correct `var/op/value` grammar.

## Decisions

**Treat the authoring guide as the source of truth.**
The guide is the author-facing contract; internal code and specs follow from it. Changing the guide to match the code would break the intended author experience and is not acceptable.

**`variant.components` overrides `node.components`; absent means inherit.**
Consistent with how `variant.text` and `variant.choices` already behave: present on the variant → use variant value; absent → fall back to node-level. No new semantics are introduced.

**No data migration step in the engine.**
The engine currently reads `variant.condition`. Existing holotape JSON files that use `condition` instead of `when` will silently stop matching after this fix. Authors must audit their content. This is acceptable because the guide has always documented `when` — any `condition` usage in content was already non-compliant.

**Reference docs are updated to match the implementation, not vice versa.**
The evaluator grammar (`var/op/value`) was always correct; the docs were wrong. Changing the evaluator to match the docs would be costly (content regeneration, re-evaluation of edge cases) for zero authoring benefit since AI agents and editors emit whichever grammar they are told to.

## Risks / Trade-offs

**Existing content using `condition` silently breaks** → Mitigation: grep all holotape JSON for `"condition"` in variant entries before deploying; update to `"when"`. The task list includes this audit step.

**No runtime warning for unknown variant fields** → The engine does not validate node shape, so a stale `condition` key will be ignored rather than reported. Low risk for a controlled content set; not worth adding validation as part of this change.

## Migration Plan

1. Audit all holotape JSON files: search for variant objects using `"condition"` key → rename to `"when"`.
2. Audit holotape JSON for inline-op condition grammar (`{ "key": ..., "eq": ... }`) → migrate to `{ "var": ..., "op": ..., "value": ... }`. (If the `dati/` directory is absent or empty, skip this step.)
3. Apply engine changes (`node-resolver.js`, `terminal.js`).
4. Update reference docs (version headers, grammar section, `not` addition).
5. Verify in browser: play a holotape that uses variants, conditional choices, and an input component.

## Open Questions

None. All six discrepancies have clear resolutions.
