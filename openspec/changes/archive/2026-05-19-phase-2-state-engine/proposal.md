## Why

After Phase 1 the Terminal can list campaigns and load holotape content from the API, but the engine still treats every holotape as a static graph of nodes and choices. The wider RobCo architecture (ARCHITECTURE.md §8) defines holotapes as **state-aware**: nodes can declare `variants` whose rendering depends on a `{ local, global }` snapshot, can emit `on_enter` mutations when they become current, and choices can carry a `set` block that mutates state on selection. Without this subsystem the API payload's `state`, `variants`, `on_enter`, and `choice.set` fields are dead weight, and no narrative authored in the backoffice can branch or remember anything.

Phase 2 builds the smallest state subsystem that honors the contract verbatim — server-authoritative, atomic per request, refresh on rejection — so Phase 3 (input components) and everything after has a real state plane to write into.

## What Changes

- **New** `src/state/store.js`: in-memory snapshot of `{ local, global }` for the active terminal session. Seeded from the `localState` / `globalState` fields of the `GET /terminals/:id/load` envelope. Exposes synchronous reads (`getLocal(name)`, `getGlobal(name)`, `getSnapshot()`) and an async `refresh()` that re-fetches the snapshot from the server. No persistence across reloads; the store resets every time a terminal is entered or re-entered.
- **New** `src/state/conditions.js`: pure evaluator for the structured condition grammar from ARCHITECTURE.md §8.6. Leaf predicates: `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in`. Combinators: `and` (list), `or` (list), `not` (single nested condition). Arbitrary nesting allowed. Pure function `evaluate(condition, snapshot) -> boolean`; no I/O, no side effects.
- **New** `src/engine/node-resolver.js`: given a node and the current snapshot, picks the first matching `variants[]` entry (or the entry marked `default: true` as fallback). Emits the node's `on_enter` mutation list, and applies the selected choice's `set` mutation list on choice selection. Variant evaluation reads the snapshot synchronously; mutations are submitted asynchronously via the mutation API.
- **New** `apiPost(path, body)` helper in `src/api/client.js` (extends the Phase 1 wrapper). JSON request body, JSON response, same normalized `ApiError` shape as `apiGet`.
- **New mutation endpoints** wired through the client:
  - `POST /terminals/:id/state/mutate` — for `local.*` mutations on the current terminal (where `:id` is `content.meta.id`, the actual terminal id).
  - `POST /campaigns/:id/state/mutate` — for `global.*` mutations within the campaign.
  - Request body: `{ "mutations": [<mutation>, …] }`. Each mutation has shape `{ "op": "set" | "increment" | "toggle", "key": "<scope>.<name>", … }`. `set` carries `value`; `increment` carries optional `by` (defaults to 1, may be negative — there is no `decrement` op); `toggle` carries neither `value` nor `by`. Each request is atomic on the server: all-or-nothing.
  - Response body: `{ "state": { <varName>: <value>, … } }` — a flat map of the post-mutation values for the scope just mutated. The engine replaces the corresponding scope in the local store from this response, so the snapshot never drifts after a successful POST.
- **Render-order decision baked in**: when entering a node, the engine evaluates `variants` against the **current local snapshot first**, renders the resolved text + choices, and **then** dispatches `on_enter` mutations. Variant rendering is never blocked on the mutation round-trip. This is locked in by the `conditional-variants` spec so it isn't relitigated later.
- **Rejection handling baked in**: on a 4xx `http` error from a mutation request, the engine calls `store.refreshScope(scope, id)` to refetch only the failing scope from the dedicated state endpoint (`GET /terminals/:id/state` for local, `GET /campaigns/:id/state` for global) and re-renders the current node against the refreshed snapshot. No optimistic apply, no last-write-wins reconciliation. (Optimistic + LWW is explicitly deferred to a future change.)
- **Mutation scope routing**: a single `on_enter` / `choice.set` list may contain a mix of `local.*` and `global.*` mutations. The engine splits the list by scope and issues at most one POST per scope per trigger. Each POST is independently atomic; if the local POST succeeds and the global POST fails, only the global is rolled back (the local mutation already applied server-side). Both responses are awaited before the next user-driven mutation is issued.
- **Backward compatibility for stateless holotapes**: a holotape whose load payload has no `state` block (or empty `state.local` / `state.global`) plays exactly as it does today. No state API calls are issued, no variant resolution runs (nodes have no `variants`), and `on_enter` / `choice.set` are absent so the resolver no-ops. Every existing holotape currently shipped by the API SHALL continue to play identically.
- **No** changes to the typewriter, sounds, keyboard nav, back history, choice rendering UI, fictional-login flow, or campaign-select. This phase only adds a state plane and rewires the node-entry / choice-select hooks through the resolver — plus a small contract-aligned tweak to the terminal-list screen described below.
- **API contract alignment — mutation wire format**: the mutation wire format follows the server contract verbatim. Field name is `key` (not `var`). Supported ops are `set`, `increment`, `toggle` only — `decrement` is NOT a server-supported op and is expressed as `increment` with a negative `by`. `increment` uses `by` (defaults to 1 on the server), never `value`. `toggle` carries no `value` or `by`. Per-endpoint scope homogeneity is required: the terminal endpoint rejects any non-`local.*` key, the campaign endpoint rejects any non-`global.*` key — the engine already splits the list by scope, so this is automatic. Holotape `on_enter` / `choice.set` mutation lists are authored in this same wire shape and forwarded as-is; no client-side translation layer.
- **API contract alignment — refresh path**: `store.refresh` is replaced by `store.refreshScope(scope, id)` which uses the dedicated `GET /terminals/:id/state` and `GET /campaigns/:id/state` endpoints instead of re-downloading the full load envelope. Refresh is scope-specific — a 4xx on the local POST refreshes only `local`, a 4xx on the global POST refreshes only `global`.
- **API contract update — hidden-terminal lookup endpoint and `MetaDto` reshape**: the server contract renames the hidden-terminal slug surface. The lookup endpoint changes from `GET /campaigns/:id/terminals/by-meta/:metaId` to `GET /campaigns/:id/terminals/by-hidden-id/:hiddenId`. On the holotape payload, `meta.id` becomes a server-injected mirror of the top-level terminal id (and is rejected on input — the client MUST NOT send it), while a new optional `meta.hiddenId` field carries the human-authored slug used by the new endpoint. The Terminal SHALL submit the secret-name input value to `by-hidden-id`; every other client→server reference to a specific terminal (visible-button `GET /terminals/:id/load`, state-refresh `GET /terminals/:id/load`, `POST /terminals/:id/state/mutate`) continues to use the actual terminal id, which the engine reads from `content.meta.id` on the load envelope. This is a small, contained change that lands inside Phase 2 because the state-mutation work introduces the very first POST traffic keyed on `terminalId`; nailing down which field the client trusts as the terminal id at the same time avoids a follow-up patch.
- **Out of scope**: input components and `input.branches` (Phase 3 — they will plug into the same store and resolver), real-user auth and per-player state scoping (Phase 4), server-side fictional login (Phase 5), service-worker cache policy for authenticated state responses (Phase 6), optimistic mutations and LWW reconciliation (deferred to a future change).

## Capabilities

### New Capabilities
- `state-store`: contract for the in-memory snapshot — seeding from the load envelope, synchronous reads, async refresh, lifecycle (cleared on terminal entry/exit), no cross-reload persistence, empty-snapshot semantics for stateless holotapes.
- `conditional-variants`: contract for `variants` resolution and `on_enter` dispatch — the structured condition grammar (`and` / `or` / `not` / `eq` / `neq` / `gt` / `gte` / `lt` / `lte` / `in`), first-match selection, `default: true` fallback, render-before-dispatch ordering, behavior when no variant matches and no default exists.
- `state-mutations`: contract for mutation dispatch — `POST /terminals/:id/state/mutate` and `POST /campaigns/:id/state/mutate`, scope routing (`local.*` vs. `global.*`), atomic per-request semantics, server rejection → refresh + re-render, no optimistic apply, no client-side validation beyond what the schema permits.

### Modified Capabilities
- `hidden-terminal-access`: the existing `Hidden terminal lookup via server by-meta endpoint` requirement is removed and replaced by `Hidden terminal lookup via server by-hidden-id endpoint`. The replacement requirement names the renamed endpoint, codifies that `meta.hiddenId` is the only slug surface (and `meta.id` is the server-injected terminal-id mirror used by every other endpoint, including the new state-mutation POSTs introduced by this phase), and adds scenarios pinning down the visible-list path and state-mutation path to the terminal id.
- `api-client`: not modified. The existing spec already permits the wrapper to grow a POST helper (it scopes itself to behaviors that "MUST NOT change" in Phase 1, not to "MUST NOT add"); the new POST surface is described entirely under `state-mutations` and does not require a delta to `api-client`.

## Impact

- **Code**: new `src/state/store.js`, new `src/state/conditions.js`, new `src/engine/node-resolver.js`. Additions to `src/api/client.js` (an `apiPost` helper using the existing `ApiError` shape). Edits to `src/main.js`#`handleTapeSelected` (seed the store from `localState` / `globalState`) and to the choice-handling and node-entry paths so they route through the resolver. The terminal-list screen, campaign-select screen, and every engine module under `src/engine/` other than the new resolver are untouched.
- **Runtime data**: the engine begins reading the `state`, `variants`, `on_enter`, and `choice.set` fields of the load envelope. The shape matches ARCHITECTURE.md §8 verbatim; no client-side schema changes required. The mutation requests issue new HTTP traffic on every node entry that has `on_enter` and every choice selection that has `set` — order of magnitude one or two POSTs per user action.
- **Network failure modes**: a mutation POST can fail with `kind: 'network'` (offline / connection refused) or `kind: 'http'` with a 4xx/5xx status. `network` and 5xx surface as a non-blocking inline error; 4xx (the "server rejected this mutation" case the architecture doc names) triggers `store.refresh()` followed by a re-render. The Terminal does not retry mutations automatically.
- **PWA / service worker**: mutation POSTs MUST NOT be cached. The current `sw.js` already passes through non-GET requests, so no change is required in Phase 2; the broader public-vs-authenticated cache split is still Phase 6.
- **Content-creator workflow**: holotape authoring in the backoffice can now use the state declaration UI, the visual condition builder, and the mutation editor end-to-end through to a running Terminal. Old holotapes authored before this phase (no `state` block) continue to play untouched, so existing content is not invalidated.
- **Existing specs preserved as-is**: `api-client`, `campaign-selection`, `typing-animation-flow`, `fast-replay-typing`, `terminal-sound-effects`, `keyboard-navigation`, `scroll-and-shortcuts`, `terminal-exit`, `file-error-back-navigation`, `login-access-control` (Phase 5 will update this), `pwa-installability` (Phase 6 will update this). `hidden-terminal-access` is updated by this phase (see Modified Capabilities).
