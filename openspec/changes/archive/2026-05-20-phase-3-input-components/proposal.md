## Why

After Phase 2 the Terminal has a real state plane (`{ local, global }` store, condition evaluator, node resolver, mutation dispatch) but the engine still only knows how to render a node as text + choice buttons. ARCHITECTURE.md §8.4 promises a third interaction primitive: a node can carry an **input component** — a typed text field whose submitted value is written into a declared state variable and routed to a target node via an ordered list of conditional branches. Without it, the only way to author "the player types a code / a name / a numeric guess and the holotape branches on the value" is to abuse the fictional-login flow, which conflates puzzle-gating (Phase 5 territory) with arbitrary value-driven branching.

Phase 3 adds the input component as a first-class node component: a CRT-styled text field rendered inside the node, submission → state mutation → branch evaluation → navigation. The existing `state-store`, `conditions`, and `state-mutations` plumbing from Phase 2 is reused verbatim; the input component is the first consumer that writes to state from a user-typed value rather than from a static `on_enter` / `choice.set` block.

## What Changes

- **New** `src/engine/components/input.js`: input-component renderer. Given a node, the component's declaration (`type: "input"`, `placeholder`, target state variable key, `branches`), and the active `terminalId` / `campaignId`, it injects a CRT-styled `<input>` + submit affordance into the choices area, captures the submitted value, writes it into the declared state variable via a single-mutation POST through the existing dispatcher, and on success evaluates `branches` (in declaration order) against the now-updated snapshot to pick a target node, then asks the terminal to `loadNode(targetId)`.
- **Component declaration** (authored in the holotape JSON under `node.components: [ ... ]`):
  - `type: "input"` — discriminator.
  - `placeholder: "..."` — placeholder text shown inside the empty field. Italian.
  - `target: "local.entered_code"` — scope-qualified state variable name the submitted value is written into. MUST be `local.*` or `global.*`. MUST be declared in the holotape's `state` block; the server enforces this, the client only checks the scope prefix.
  - `branches: [ { condition, target }, ..., { default: true, target } ]` — ordered list. Each entry has either a structured `condition` (same grammar as `variants`, ARCHITECTURE.md §8.6) or `default: true`. The first entry whose condition evaluates true against the **post-mutation snapshot** wins. A `default: true` entry is the fallback. No matching branch + no default → engine error surfaced as an inline state error (the holotape is malformed).
- **Submission semantics**: pressing Enter (or clicking the submit button) writes the raw input value to the declared state variable as a `{ op: 'set', key: <target>, value: <string> }` mutation, dispatched through the Phase 2 mutation dispatcher (so the existing scope-routing, atomicity, and rejection handling apply). On 2xx the local store's corresponding scope is replaced from the response's `state` map (Phase 2 contract), the resolver evaluates `branches` against the refreshed snapshot, and the engine navigates to the matching branch's `target`. On a 4xx the engine refreshes the failing scope and re-renders the current node (no navigation). On a 5xx / network error the engine surfaces an inline non-blocking error and leaves the field intact so the user can retry.
- **Value typing**: in Phase 3 the submitted value is always sent as a **string** (the raw field value). The server validates the type against the declared variable schema; a string-typed variable accepts it directly, and an enum-typed variable accepts it iff the string matches one of the declared enum values. Authoring a `number`-typed target is out of scope for this phase (the input has no numeric mode and no parse step) and the server will reject such a submission with a 400. A later change may add `inputType: "number"` with client-side parse.
- **One component per node, replaces the choice list**: a node MAY declare at most one entry in `components` with `type: "input"`. When present, it is rendered in place of the node's `choices` (choices, if also declared, are ignored when an input component is present). The system-level "back" / "disconnect terminal" affordances continue to render below the input field exactly as they render below choice buttons today.
- **CRT styling**: a new selector `#choices-container .input-field` (CSS class applied to the rendered `<input>`) reuses the same visual rules as `#login-screen input[type="password"]` and `#hidden-input` in `src/styles/terminal.css` — transparent background, green phosphor border, inherited monospace font, green text-shadow. The submit affordance is rendered as a standard `.choice-btn` so keyboard navigation (ArrowUp/ArrowDown/Enter) treats it as just another button in the choices list.
- **Keyboard behavior**: focus lands on the input field on render. Enter submits. ArrowDown/ArrowUp move focus between input and submit (and any system buttons), consistent with the existing `makeNavHandler` pattern. Escape behaves like in the choice list: if there is back-history, navigate back; otherwise disconnect.
- **Engine wiring**: `src/screens/terminal.js#renderNode` detects when the resolved view declares an input component and delegates rendering to the new module instead of calling `showChoices`. The fictional-login flow is untouched — it remains a separate gate that runs before component rendering (the existing `getLoginForNode` early-return in `loadNode` is preserved).
- **Backward compatibility**: nodes that don't declare `components` (every existing holotape) render exactly as today through `showChoices`. The input component is purely additive — no existing node shape gains or loses behavior.
- **Out of scope**: numeric / boolean / enum input affordances (everything goes through a single string field with server-side validation), client-side input validation beyond non-empty, multi-line input, password-masked input, multi-component nodes, components other than `type: "input"`, replacing the fictional-login screen with an input component (Phase 5), real-user auth (Phase 4), service-worker cache changes (Phase 6).

## Impact

- **Code**: new `src/engine/components/input.js`. Edits to `src/screens/terminal.js`: `renderNode` branches between `showChoices` and the new component renderer when `view.components` contains an input entry. Small CSS addition in `src/styles/terminal.css` for `.input-field`. No edits to `src/state/store.js`, `src/state/conditions.js`, `src/engine/node-resolver.js`, or `src/api/client.js` — the component reuses the existing exports (`getSnapshot`, `evaluate`, `dispatchOnEnter` style POST through the existing mutation surface, `applyScope` on response).
- **Runtime data**: the engine begins reading `node.components[]` for the first time. Existing payloads without `components` are unaffected. A holotape that declares an input component issues one additional `POST /terminals/:id/state/mutate` or `POST /campaigns/:id/state/mutate` per input submission — the same POST traffic Phase 2 already established, just user-triggered instead of `on_enter`-triggered.
- **Network failure modes**: identical to Phase 2 — `kind: 'network'` / 5xx → inline error, field stays mounted, user can retry; `kind: 'http'` 4xx → scope refresh + re-render of the current node (the input field is re-rendered empty against the refreshed snapshot).
- **PWA / service worker**: no change. The mutation POST is the same shape Phase 2 introduced; `sw.js` already passes non-GET requests through.
- **Content-creator workflow**: holotape authors gain a new authoring primitive — `node.components: [{ type: "input", placeholder, target, branches: [...] }]` — that replaces the current "abuse fictional-login for a code-entry puzzle" pattern. The `super_duper_admin.json` puzzle ("digita il codice `58874645`") becomes expressible as a node with one input component and two branches (`condition: { var: 'local.entered_code', op: 'eq', value: '58874645' }` → success node; `default: true` → retry node). The fictional-login flow is preserved for actual login gating, not value-driven branching.
- **Specs preserved as-is**: `state-store`, `conditional-variants`, `state-mutations`, `hidden-terminal-access`, `api-client`, `campaign-selection`, `typing-animation-flow`, `fast-replay-typing`, `terminal-sound-effects`, `keyboard-navigation`, `scroll-and-shortcuts`, `terminal-exit`, `file-error-back-navigation`. `login-access-control` (Phase 5) and `pwa-installability` (Phase 6) remain on their own phases.
